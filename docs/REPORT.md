# REPORT.md

本文件定义 Legal-Assistant_agent 的专业最终报告规则。最终报告不是概述，也不是把工作底稿合并成一份长文，而是把事项文件夹中的事实、证据、来源、法律推理、风险判断和行动建议，重写成一份可供当事人、律师或法律工作者阅读、复核和继续使用的专业交付件。

## 1. 触发条件

出现以下任一情况，必须生成或更新专业最终报告：

- 用户要求“总结、汇总、最终报告、给我一份文件、生成 PDF”。若用户只是要求分析，默认先输出会话汇总结论，不自动生成 PDF。
- 复杂案件、合同审查、合同起草或法律研究完成一个阶段。
- 已完成多个阶段的事实整理、证据分析、法律研究或策略设计，需要合并成可交付成果。
- 出现新证据、新程序节点、新合同版本、新报价，需要复盘后重新交付。

### 2A. 复核版报告规则

如果事项文件夹已存在报告，本轮又收到同一事项的新说明、补充事实或用户要求继续推进：

- 先判断是否复用既有事项文件夹，并在报告封面或“分析范围与可靠性说明”中写明本轮状态，例如“复用既有事项文件夹，已复核来源和报告主线”。
- 不要把旧报告简单改日期。必须重新读取工作文件、检查 gate、复核来源状态，并确认报告状态仍然匹配证据强度。
- 若事实证据仍未上传或关键证据未读取，报告状态保持 `draft`；只有内容 gate 和证据 gate 真正通过时才可升级。
- 若更新了来源、日期、内部推进状态、质量检查或关键判断，必须同步更新 `plan.md`、`case.md` 或 `sources.md` 中对应记录。
- 已请求 PDF 时，专业报告 PDF（.pdf）与专业报告 Markdown（.md）必须同源；更新专业报告 Markdown（.md）后，旧 PDF 不得继续标记为 ready，除非已重新渲染并通过质量检查。未请求 PDF 时，PDF 状态写为 `not requested`，不标记 blocked。

### 2B. 报告定位、读者与范围

生成报告前，先判断这份报告要服务谁、支持什么决策。不同读者需要的深度和语言不同，但都必须保留可复核的事实、证据、依据和限制。

| 读者 | 报告重点 | 表达要求 |
|---|---|---|
| 普通用户/当事人 | 当前能判断什么、不能判断什么、最应该补什么、下一步怎么做 | 先讲结论和风险，再解释依据；少用行话，必要术语要解释 |
| 律师/法律工作者 | 争议焦点、请求权基础、证明责任、证据链、程序路径、文书入口 | 保留专业结构、推理路径和证据缺口，便于接手办理 |
| 企业/业务决策者 | 责任边界、金额区间、谈判筹码、执行成本、合规风险 | 强调商业后果、可选路径、成本和触发条件 |
| 合同审查/交易团队 | 条款风险、风险分配、替代条款、谈判优先级和签署前检查 | 条款结论必须落到具体修改建议或谈判方案 |

报告范围必须写清：

- 本报告覆盖哪些法律问题、程序阶段、合同版本或交易结构。
- 本报告未覆盖哪些问题，未覆盖原因是什么。
- 哪些结论可用于谈判、沟通或内部决策，哪些结论仍需律师核验、官方来源核验或原始证据确认。
- 如用户只要求阶段分析，不应伪装成完整法律意见；如用户要求最终报告，则必须说明报告的阶段性边界。

### 2C. 工作文件吸收规则

前期生成的工作文件不是附件清单，而是报告正文的材料来源。最终报告必须把这些文件转化为读者能理解的实体内容，不能只写“已读取/已生成”。

| 工作文件 | 报告中应转化为 | 不应写成 |
|---|---|---|
| `plan.md` | 报告用途、阶段状态、下一步、待用户补充事项 | 内部 PDCA 表或 gate 表 |
| `case.md` | 事项地图、关键事实、程序状态、核心争议焦点 | 原始事实堆叠 |
| `case_dashboard.md` | 关键影响因素、争议焦点关系图、证明责任、可信度 | 文件摘要或路径列表 |
| `consultation_note.md` | 用户可读的当前判断、限制、补证材料和不宜采取的动作提醒 | 内部咨询记录全文 |
| `case_package.md` | 案件主线、攻防结构、文书/庭审准备入口 | 另一份案件包复制件 |
| `timeline.md` | 服务争议焦点和证明责任的事实时间线 | 单纯日期流水账 |
| `evidence.md` | 证据链、证明对象、三性风险、补强动作 | 证据名称列表 |
| `sources.md` | 法律依据、来源层级、适用边界、引用风险 | 法条或链接堆砌 |
| `analysis.md` | 争议焦点分析、推断链、反制路径、金额/风险区间 | 未整理的推理底稿 |
| `advice.md` | 可执行策略、谈判路径、行动清单和表达风险 | 泛泛建议 |
| `drafts.md` / `pleading_framework.md` / `hearing_playbook.md` | 文书、庭审或沟通方案入口 | 未经筛选的草稿集合 |
| `contract.md` / `clause_review.md` / `term_sheet.md` / `contract_draft.md` | 合同结构、条款风险、修改建议、草案正文或谈判选择 | 条款复制粘贴 |
| `skill_outputs.md` | 内部核对依据，确保已执行 skill 的关键发现进入相应章节 | 面向读者展示 skill 表、执行日志或内部状态 |

如果某个重要工作文件缺失，应在“分析范围与可靠性说明”中改写成读者能理解的限制，例如“尚未形成证据台账，证据强度判断仅为初步评估”，而不是写“未执行某 skill”。

### 2D. 专业写作口径

报告语言应当像法律备忘录、案件分析报告或合同审查意见，而不是 AI 摘要。默认采用“结论先行、依据紧随、限制明确、动作落地”的写法。

必须做到：

- 先区分事实、证据、推断、法律评价和策略建议。
- 每个关键判断都写清“基于哪些材料、适用什么规则、在什么条件下成立、对方可能如何反驳、当前不确定性是什么”。
- 多用“根据目前材料”“在该事实能够被证明的前提下”“若对方能够证明……则结论可能变化”等条件化表达。
- 少用空泛措辞，例如“存在一定风险”“建议咨询律师”“结果可能性较高/较低”。必须说明风险来自哪里、会影响什么、如何补强。
- 不把用户目标直接写成法律结论，不把用户陈述直接写成已证明事实。
- 法条、案例和政策必须服务于本案适用边界；不能只列名称、条文或网页链接。
- 金额、概率、结果可能性和谈判锚点必须绑定计算口径、证据状态和替代情形。
- 结尾要落到可执行动作：谁负责、做什么、为什么做、触发条件和产物是什么。

## 4. 专业报告基础结构

本节不是固定模板，也不是要求所有报告都使用同一套标题。它定义的是专业报告必须覆盖的信息域和最低论证深度。实际执行时，可以根据事项类型、材料成熟度、目标读者和程序阶段调整标题、顺序和篇幅；复杂案件应充分展开，简单事项可以压缩，但不能省略影响可靠性的内容，例如分析范围、材料限制、来源状态、证据状态、待补信息和 PDF 请求状态。

专业报告的每个核心章节都应回答四个问题：

1. 这一部分解决什么决策问题。
2. 依据哪些事实、证据、合同条款或来源。
3. 当前结论的适用条件、反方解释和不确定性是什么。
4. 读者下一步应该做什么。

### 4.1 封面与阅读入口

报告开头应让读者快速理解“这是什么事、报告能解决什么、哪些内容不能当作确定结论”：

- 本地化标题、事项类型、输出语言、生成日期、事项文件夹。
- 重要提示：本报告为法律信息整理和分析辅助，不替代律师意见。
- 报告状态：`complete / complete_except_pdf / draft / incomplete`。
- 一段不超过 150 字的阅读说明：本报告依据哪些材料、用于什么决策场景。
- 目录。长报告必须有目录；短报告可以用清晰的章节标题代替。

报告状态必须与 gate 状态一致：

| 状态 | 对读者的含义 | 常见触发 |
|---|---|---|
| `complete` | 内容、来源、证据、报告和会话展示均已通过基础检查；未请求 PDF 时也可为 complete | 已完成必要来源核验、证据状态说明和会话展示检查；若已请求 PDF，PDF 也已通过质量检查 |
| `complete_except_pdf` | 用户已请求 PDF，内容已可作为完整阶段成果，但 PDF 生成或质量检查失败 | 仅 PDF Gate blocked，其他 gate 已通过 |
| `draft` | 已形成阶段性分析，但事实、证据、来源或程序信息仍有关键限制 | Source Gate blocked、关键证据未上传、程序节点待确认 |
| `incomplete` | 必要环节未执行或关键输入缺失，不能作为完整分析使用 | 必跑 skill 缺失、事项未路由、核心材料未读取 |

Source Gate blocked 时，不得使用 `complete_except_pdf`。即使专业报告 Markdown（.md）已经生成，也应标记为 `draft` 或 `incomplete`，并说明哪些法律依据仍待官方/权威来源核验。

未请求 PDF 时，PDF Gate 应写为 `skipped / not requested`，不得把 PDF 缺失写成失败。

### 4.2 执行摘要

执行摘要应先给读者可行动的判断，再解释依据。建议包含 3-5 条核心结论，每条结论必须绑定结论等级、依据、证据状态、主要风险和下一步。复杂事项的摘要不应只写结果，还要说明该结果依赖哪几个前置争议焦点。

| 结论 | 等级 | 依据 | 证据状态 | 主要风险 | 下一步 |
|---|---|---|---|---|---|

结论等级可使用“相对稳固 / 条件性成立 / 需要补证 / 待核验规则 / 不建议依赖”。摘要不能写成泛泛的“有一定风险/建议咨询律师”。如果结论受限于未上传证据、未联网核验或程序信息不足，应直接说明限制。

### 4.3 报告范围、材料与方法

说明本轮报告依据哪些事实、证据、合同文本、沟通记录、法律来源或工作底稿，哪些材料缺失，哪些事实仍只是用户陈述。报告范围不只是“材料清单”，还要说明“本报告分析什么、不分析什么、为什么”。

| 材料/来源 | 是否已核验/读取 | 用途 | 对结论影响 |
|---|---|---|---|

至少覆盖：用户输入、关键证据、合同/文书、案件驾驶舱、咨询纪要、案件包、时间线、证据台账、法律来源、分析底稿、行动建议和已生成草稿。内部工作文件可以作为生成依据，但报告正文不应把 `skill_outputs.md`、gate 表或 skill 执行细节展示给普通阅读对象。

必要时增加范围表：

| 范围项目 | 本报告处理方式 | 未处理/限制 | 原因 |
|---|---|---|---|
| 事实问题 |  |  |  |
| 证据问题 |  |  |  |
| 法律规则适用 |  |  |  |
| 程序路径 |  |  |  |
| 金额测算 |  |  |  |
| 谈判/行动 |  |  |  |

### 4.4 分析范围与可靠性说明

这一部分只向阅读对象说明“本报告能支持什么判断、哪些判断仍受材料限制”，不展示内部 skill 名称、gate 名称、执行索引或 PDCA 表。内部完整性检查仍写入 `plan.md` 和 `skill_outputs.md`。

| 项目 | 内容 |
|---|---|
| 报告用途 | 例如谈判评估、仲裁准备、合同签署前审查、法律研究备忘 |
| 结论等级 | 可分为“相对稳固 / 条件性成立 / 需要补证 / 待核验规则 / 不建议依赖” |
| 已核验材料 | 已读取或核验的合同、证据、来源、程序材料 |
| 未核验材料 | 尚未取得、仅凭用户陈述或需第三方调取的材料 |
| 主要限制 | 对金额、结果可能性、管辖、期限、证据采信或执行可行性的影响 |
| 更新触发 | 新证据、新报价、新程序节点、新合同版本或新法规变化 |

如果内部检查发现必需环节未完成，不要在报告中写“某内部阶段未执行”。应改写为阅读对象能理解的限制，例如“尚未核验原始合同文本”“未取得银行流水，金额判断仅为框架性分析”“未完成类案检索，裁判倾向仅作一般规则判断”。

如果限制来自来源核验，应写成：

```text
本报告尚未完成官方/权威来源核验。涉及法律依据、监管口径、类案裁判或时效期限的内容仅作为待核验分析框架，不宜直接用于提交材料或作为最终法律意见。
```

如果限制仅来自 PDF 渲染，应写成：

```text
本报告的 Markdown 版本已完成阶段性内容检查，但当前环境未能生成通过质量检查的 PDF。PDF 状态为 blocked，不影响 Markdown 内容本身的阶段性完整性。
```

仅在用户已要求 PDF 且渲染失败时使用上述表述。若用户未要求 PDF，应写成：

```text
本轮默认先提供会话汇总结论。尚未生成 PDF；如需正式 PDF 专业报告，可继续提出。
```

### 4.5 事项地图与程序状态

用一页以内说明当事人角色、法律关系、关键行为、用户目标、对方主张、程序阶段和当前最重要的判断入口。若存在 `case_dashboard.md`，应吸收其中的一句话地图、三个关键影响因素、争议焦点关系图和可信度，而不是简单复制原文。多程序案件必须拆分谈判、仲裁/诉讼、行政投诉、税务/社保/公积金投诉、执行或和解等战场。

复杂事项的事项地图至少说明：

- 谁向谁主张什么，基于什么法律关系或合同关系。
- 当前真正影响结果的 2-4 个关键影响因素是什么。
- 哪些程序或战场相互影响，例如谈判让步会影响诉讼主张、行政投诉会影响证据取得或和解压力。
- 哪些问题已经进入程序，哪些仍停留在谈判、补证或待决策阶段。

### 4.5A 咨询纪要与案件包摘要

复杂案件已生成 `consultation_note.md` 或 `case_package.md` 时，最终报告应把其中内容转化为两个读者友好的入口：

- 对用户：当前可以相信什么、不能相信什么、需要补什么、不能做什么。
- 对法律工作者：本案主线、证明路径、攻防位置、文书/庭审准备入口。

本节不展示内部文件名清单，而是把工作台产物整理为报告正文。若案件工作台文件缺失，应在“分析范围与可靠性说明”中说明影响。

### 4.6 事实时间线

时间线应服务于争议焦点和证明责任，不只是罗列日期。每个重要节点应说明证据状态和法律影响。

| 时间 | 事件 | 证据 | 争议状态 | 影响 |
|---|---|---|---|---|

### 4.7 争议焦点总览与争议焦点关系

复杂纠纷必须先把问题讲清楚，再进入结论。争议焦点分析至少包括核心争议焦点矩阵、争议焦点依赖关系和争议焦点展开。

| 编号 | 争议焦点 | 类型 | 证明责任 | 用户立场 | 对方立场 | 证据 | 缺口 | 影响 |
|---|---|---|---|---|---|---|---|---|

争议焦点关系可用文字链条、关系表或已渲染的流程图展示。不能渲染流程图时，使用关系表，不保留 Mermaid 源码。

| 前置争议焦点 | 影响的后续争议焦点 | 关系说明 | 失败后果 |
|---|---|---|---|

争议焦点展开必须体现母命题、条件命题、反制命题、金额命题、程序命题和证据命题之间的关系。

| 层级 | 命题 | 依赖事实 | 支撑证据 | 对方替代解释 | 对其他争议焦点影响 |
|---|---|---|---|---|---|

每个核心争议焦点应按以下逻辑展开，避免停留在“列争议焦点”：

- 争议焦点问题：裁判者或审稿者真正需要判断的问题是什么。
- 己方命题：用户希望证明什么，证明后能支持什么请求或谈判目标。
- 对方命题：对方最可能否认什么、承认后如何重新解释、会提交什么反证。
- 证明责任：谁负主要证明责任，谁负反驳或说明责任。
- 现有证据：哪些证据直接证明，哪些只是间接支持，哪些仍为用户陈述。
- 法律规则适用：规则成立需要哪些条件，本案哪些条件满足，哪些条件待证。
- 影响结果：该争议焦点若成立/不成立，会影响哪些后续争议焦点、金额或程序选择。

### 4.8 请求权基础、证明责任与证据链

把“想要什么”拆成“要证明什么、谁来证明、已有证据够不够”。这一部分应同时服务于法律判断、谈判筹码和下一步补证。

| 请求/抗辩 | 法律路径 | 要件 | 待证明事实 | 责任方 | 现有证据 | 对方攻击 | 下一步 |
|---|---|---|---|---|---|---|---|

| 证据 | 证明对象 | 强度 | 三性风险 | 缺口 | 补强动作 |
|---|---|---|---|---|---|

如果用户同时有多个请求或抗辩，应区分主路径、备选路径和兜底路径。例如“合同请求权优先、不当得利兜底、侵权或缔约过失仅在特定事实成立时讨论”。不得把所有可能路径平铺为同等强度。

### 4.9 法律依据与法律规则适用边界

引用法律、案例、政策或网页时，必须说明来源状态和适用边界。不能只贴法条名称或把个案裁判观点写成必然结论。

| 来源 | 机构 | URL | 核验状态 | 可用规则 | 引用风险 |
|---|---|---|---|---|---|

| 规则 | 适用条件 | 例外/限制 | 证明要求 | 对本案可用性 | 引用风险 |
|---|---|---|---|---|---|

每条核心法律规则至少说明：

- 法域和时间效力：规则适用于哪个国家/地区、哪个时间段。
- 主体边界：适用于劳动者、消费者、公司、平台、雇主、交易相对方还是其他主体。
- 行为边界：规则覆盖的是违约、侵权、行政违法、劳动争议、合同解释还是证据规则。
- 证明边界：需要证明哪些事实，哪些事实由对方承担说明或反证责任。
- 后果边界：规则支持的是确认、给付、赔偿、返还、解除、撤销、罚款、补缴还是程序性救济。
- 类案边界：类案只能说明裁判思路或风险，不得写成同案必然结果。

### 4.10 对方视角与裁判者视角

报告必须主动呈现不利面：对方可能如何解释事实、攻击证据、压低金额或提出反请求；法官、仲裁员、调解员或审稿律师会按什么顺序审查。该部分不是“替对方说话”，而是帮助读者提前看到最可能改变结论的事实和证据。

| 视角 | 可能关注 | 对己方影响 | 应对方式 |
|---|---|---|---|
| 对方 |  |  |  |
| 裁判者/审稿者 |  |  |  |
| 调解/谈判方 |  |  |  |

### 4.11 金额、风险区间与策略路径

所有金额、概率和结果可能性判断都必须绑定假设、证据状态和不确定性，不能给绝对承诺。策略建议应分层：低冲突路径、中冲突路径、高强度路径，并说明触发条件。

| 优先级 | 责任方 | 动作 | 目的 | 触发条件 | 产物 |
|---|---|---|---|---|---|

金额和风险区间建议使用“保守 / 基准 / 进取”三档，但必须说明计算口径：

| 项目 | 保守口径 | 基准口径 | 进取口径 | 关键假设 | 证据限制 |
|---|---|---|---|---|---|

策略路径应写成可执行方案，不只是“建议协商/建议仲裁”。至少说明：

- 启动条件：什么事实、证据或报价出现后进入该路径。
- 成本和风险：时间、证据、费用、关系、败诉或反请求风险。
- 沟通口径：哪些表达可用，哪些表达会削弱主张。
- 退出条件：何时应停止谈判、转入投诉/仲裁/诉讼，或接受和解。

## 5. 合同类报告调整

合同审查报告不能只给“高/中/低风险”标签。每个风险必须说明风险触发条件、责任后果、可接受替代方案和谈判优先级。

合同审查报告必须保留：

- 合同背景、用户角色、合同版本、签署状态。
- 条款摘要。
- 高/中/低风险清单。
- 缺失条款。
- 建议修改稿。
- 谈判优先级。
- 签署前核验清单。
- 来源和引用风险。
- 分析范围与可靠性说明。

合同审查中每个高风险条款建议使用以下结构：

| 条款 | 风险类型 | 触发条件 | 对用户影响 | 建议改法 | 可接受底线 | 谈判优先级 |
|---|---|---|---|---|---|---|

合同起草报告必须保留：

- 起草前提和待确认信息。
- 交易结构。
- 条款结构。
- 合同草案正文。
- 可谈判条款。
- 签署前核验清单。
- 风险提示和来源引用。
- 分析范围与可靠性说明。

合同起草报告应把“商业目标”转化为“条款选择”。对于关键条款，应说明为什么采用该版本、对用户有利在哪里、对方可能要求什么替代版本，以及可以让步到什么程度。

## 5A. 法律研究、文书和复盘报告调整

法律研究报告必须保留：

- 研究问题和适用法域。
- 结论摘要和可引用等级。
- 官方/权威来源分层。
- 规则要件、例外、适用边界和类案边界。
- 对当前事项的适用分析。
- 未核验来源和不可直接引用风险。

文书或诉讼/仲裁准备类报告必须保留：

- 文书目标和目标读者。
- 请求、抗辩或沟通目标。
- 事实叙事顺序。
- 证据附件和证明对象。
- 法律依据和法律规则适用边界。
- 表达风险、高风险表述和替代表达。

复盘报告必须保留：

- 新旧事实、证据、来源或程序节点的变化。
- 哪些原判断被加强、削弱或推翻。
- 哪些 skill 或工作文件需要重跑或更新。
- 报告状态是否升级、降级或保持不变。
- 下一轮最小有效行动。

## 6. 会话界面展示

会话界面不是报告目录，也不是文件路径清单。最终回复应像一份可直接阅读的 briefing：先讲结论和限制，再讲依据、来源、风险和下一步。回复必须使用用户主语言，且应从事项文件夹和最终报告中提取实质内容。

### 6.2 信息引用要求

会话展示至少引用以下参考信息，避免用户只看到结论：

- 从 `case.md` 引用事项地图、关键事实、程序状态。
- 从 `case_dashboard.md` 引用三个关键影响因素、争议焦点关系图、证明责任、证据缺口和当前可信度；若缺失，应说明未生成案件驾驶舱。
- 从 `consultation_note.md` 引用用户能直接理解的当前判断、限制、补证材料和不宜采取的动作；若缺失，应说明当前回复仅为分析报告摘要。
- 从 `case_package.md` 引用案件主线、攻防结构、文书/庭审准备入口；若缺失，应说明尚未形成深度案件包。
- 从内部执行记录提取关键发现和未解决问题，但不要在会话中展示 skill 名称、执行索引或 gate 细节。
- 从 `evidence.md` 或 `analysis.md` 引用关键证据缺口和推断链。
- 从 `sources.md` 引用来源数量、来源类型、核心规则和引用风险。
- 从最终报告引用核心结论、争议焦点关系、最大风险和行动清单。

如果某个文件不存在或未读取，必须写明“未见/未读取/不适用”，不能暗示已经完成。

### 6.3 展示深度

- 简单事项：会话回复可以压缩，但至少保留核心结论、来源状态、最大风险、下一步和文件路径。
- 复杂纠纷：会话回复必须展示争议焦点关系、证明责任、证据缺口、来源核验和策略路径，不能只写三句话摘要。
- 合同审查：会话回复必须展示高风险条款、可接受条款、需修改条款、签署前清单和来源/监管核验状态。
- 合同起草：会话回复必须展示交易结构、核心条款选择、待确认事项、签署风险和草案路径。
- 法律研究：会话回复必须展示问题结论、来源分层、适用边界和不可引用风险。

如果用户已要求 PDF，但 PDF 生成失败或质量不合格，必须写明：

- Markdown 已生成路径。
- PDF 状态：blocked。
- 阻塞原因。
- 建议转换方式。

如果用户未要求 PDF，最终回复应简短提示“如需正式 PDF 专业报告，可以继续提出”，但不要把 PDF 作为本轮交付失败项。

## 7. PDF 导出质量门槛

用户明确要求 PDF 后，合格 PDF 必须满足：

- 文件真实存在且大小非空。
- 中文、英文、数字、表格基本可读。
- 表格已渲染为真实表格，不出现 Markdown 管道符或 `|---|---|`。
- Mermaid、flowchart、HTML 或 Markdown 代码块没有以源码形式出现在正文。
- 不出现明显乱码、缺字、项目符号异常、标题挤压、表格严重溢出或目录错乱。
- 专业报告 Markdown（.md）和专业报告 PDF（.pdf）内容一致。
- PDF 与本轮 Markdown 同源生成；如果 Markdown 更新，旧 PDF 不得继续标记为 ready。

优先使用支持 CJK 字体、表格、页眉页脚和分页的非浏览器导出方式。可用路径包括 Pandoc+DOCX-to-PDF、Pandoc+XeLaTeX、WeasyPrint、wkhtmltopdf、ReportLab/PDFKit、根目录 `tools/render_report_pdf.py` 或宿主文档工具。可用 styled HTML 路径时，优先引用或内联 `assets/legal-report.css`，形成白底卡片、蓝紫青强调、编号胶囊、浅色数据表、双语导航、风险/来源提示区块的 PDF。若使用根目录渲染器，输入目录即输出目录，只在事项文件夹生成专业报告 PDF（.pdf），不复制脚本或样式文件。默认不得使用 Chrome headless、Chromium、Edge、Playwright、Puppeteer、Selenium 或系统浏览器打印生成 PDF；除非用户明确允许浏览器渲染。若用户已要求 PDF，但无法确认中文字体、表格、图形和源码残留检查，不得报告“PDF 已完成”，而应在 `plan.md` 和会话中标记 blocked。

## 8. 禁止事项

- 禁止把最终报告写成几段概述。
- 禁止只列“已生成文件路径”而不展示实质分析。
- 禁止缺少争议焦点关系图、推断链条和法律规则适用边界。
- 禁止遗漏内部 `skill_outputs.md` 检查，但不得把 skill 执行表当作面向阅读对象的报告内容。
- 禁止遗漏“分析范围与可靠性说明”。
- 禁止引用来源但不写入 `sources.md`。
- 禁止把 Markdown 原文直接作为 PDF 内容交付。
- 禁止交付乱码、未渲染表格或残留 Mermaid 源码的 PDF。
- 禁止把未经核验的法条、案例或网页写成已核验结论。
