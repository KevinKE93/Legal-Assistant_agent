# CASE_WORKBENCH.md

本文件定义 Legal-Assistant_agent 的“案件工作台”模式。它面向律师、法律助理、仲裁/诉讼团队和法律咨询工作者，用于把零散事实快速转化为可讨论、可补证、可写文书、可准备庭审的事项包。

案件工作台不是新的代码运行时，也不是额外安装器。它是在现有纯文档工作流中增加一组更适合法律工作者使用的交付物和质量门槛。

## 1. 触发条件

案件工作台只在 `Deep Case` 模式下启用。出现以下任一情况时，才考虑进入案件工作台模式：

- 用户描述纠纷、索赔、返还、赔偿、解除、违约、侵权、劳动争议、仲裁、诉讼、投诉或听证。
- 对方已经提出主张、抗辩、反请求、答辩、和解报价或行政处理意见。
- 用户需要持续的案件分析、证据整理、谈判策略、文书框架或庭审准备，且会话回复或 `matter.md` 已不足以承载。
- 新证据、新程序节点、新合同版本、新报价或对方材料改变了既有判断。

简单法律问答只输出对话答案；需要持续记忆但不复杂时，只维护 `matter.md`。不要因为出现“纠纷”二字就自动生成案件工作台。

以下事项通常不进入案件工作台，除非同时出现争议、对方抗辩、程序节点或听证准备：

- 签署前合同审查。
- 合同起草或条款清单整理。
- 纯法律研究或法规检索备忘。
- 常规合规问题梳理。

这类事项在 `matter.md` 或会话回复中可写：

```text
Workbench: not needed
Reason: 本事项为合同审查/合同起草/法律研究，无既有争议或程序节点。
Trigger to revisit: 若后续出现违约争议、对方抗辩、谈判僵局、仲裁/诉讼或听证准备，再进入 Deep Case。
```

## 2. 两种工作速度

案件工作台按两种速度推进。

### 2.1 快速咨询层

初次接触复杂事项时，应优先在 3-5 分钟内形成两个轻量文件：

```text
case_dashboard.md
consultation_note.md
```

目标不是直接完成报告，而是给法律工作者和用户一个清晰入口：

```text
杂乱事实
→ 案件驾驶舱
→ 可说明给用户的咨询纪要
→ 决定是否补证、检索、起草、谈判或进入深度案件包
```

### 2.2 深度案件包层

当证据、合同、对方材料、程序材料或来源研究具备一定基础后，再生成：

```text
case_package.md
pleading_framework.md
hearing_playbook.md
```

其中 `case_package.md` 是法律团队的工作案件包，报告是对它和其他工作文件的再组织、再表达和对外交付版本。两者不能互相替代。

## 3. 工作台核心文件

| 文件 | 读者 | 作用 | 生成时机 |
|---|---|---|---|
| `case_dashboard.md` | 律师、法律助理、咨询人员 | 一页式案件地图，帮助快速判断主线、争议焦点、证据缺口和风险 | 初次复杂事项摄入后优先生成 |
| `consultation_note.md` | 用户、客户、咨询接待人员 | 用更通俗语言说明当前能判断什么、不能判断什么、还要补什么 | `case_dashboard.md` 后生成 |
| `case_package.md` | 法律工作团队 | 串联事实、证据、争议焦点、来源、对方视角、裁判视角和策略 | 证据/来源/分析阶段完成后生成 |
| `pleading_framework.md` | 文书起草人员 | 形成仲裁申请、起诉状、答辩、代理意见或投诉材料的骨架 | 用户需要文书、已进入程序或准备提起程序时 |
| `hearing_playbook.md` | 庭审/听证准备人员 | 准备举证顺序、质证、发问、裁判者追问和安全答法 | 调解、仲裁、开庭、听证前 |
| `review_delta.md` | 复盘人员 | 记录新材料改变了什么、哪些判断要重跑、哪些文件要更新 | 新事实、新证据、新程序节点或新报价出现时 |

## 4. case_dashboard.md

`case_dashboard.md` 是案件工作台的第一屏。它回答：

```text
现在这个案件应当如何理解？
```

必须短、准、可扫描，不写成长报告。默认结构：

```markdown
# 案件驾驶舱

## 1. 案件一句话地图

## 2. 程序状态

## 3. 关键判断变量
| 关键问题 | 为什么关键 | 当前证据状态 | 最大风险 |
|---|---|---|---|

## 4. 争议焦点关系图
| 层级 | 争议焦点 | 依赖事实 | 影响 |
|---|---|---|---|

## 5. 证明责任与证据缺口
| 要证明什么 | 责任方 | 现有证据 | 缺口 | 风险 |
|---|---|---|---|---|

## 6. 对方打法
| 对方可能说法 | 攻击目标 | 可用反制 | 风险 |
|---|---|---|---|

## 7. 法律依据状态
| 规则/来源 | 核验状态 | 可用性 | 引用风险 |
|---|---|---|---|

## 8. 当前判断可信度
| 维度 | 状态 | 说明 |
|---|---|---|
| 事实可信度 |  |  |
| 证据完整度 |  |  |
| 来源核验度 |  |  |
| 程序不确定性 |  |  |
```

约束：

- 不在本文件写“下一步五个动作”或输出分流；行动计划写入 `matter.md`、会话回复或 `case_package.md`。
- 用户单方陈述必须标为待证明，不能写成已证明事实。
- 法律来源未检索时必须写“待核验”，不能写“已核验”。

## 5. consultation_note.md

`consultation_note.md` 是面向用户或客户的咨询纪要。它从案件驾驶舱提炼，但用更自然的语言表达。

必须包含：

- 当前可以初步判断的事项。
- 当前不能判断或不能下结论的事项。
- 对用户最重要的 3-5 个法律/证据/程序风险。
- 用户应补充的材料清单。
- 用户暂时不宜做的表达或动作。
- 下一次协作需要用户提供什么。

语气要求：

- 清楚、克制、能被非律师理解。
- 不夸大结果倾向，不承诺结果。
- 必要法律术语要用一句话解释。

## 6. case_package.md

`case_package.md` 是工作文件，不是报告。它用于帮助法律团队继续起草、谈判、开庭或复盘。

建议结构：

1. 案件驾驶舱摘要。
2. 事实时间线。
3. 证据目录与证明对象。
4. 争议焦点关系图与依赖关系。
5. 请求权基础与证明责任。
6. 法律依据与法律规则适用边界。
7. 对方视角与反制计划。
8. 裁判者视角。
9. 策略路径。
10. 文书与庭审准备索引。
11. 待补问题和材料请求。

每个关键判断都必须能追溯到事实、证据、来源或明确假设。

## 7. pleading_framework.md

当用户需要文书、已经进入程序或准备发函/投诉/仲裁/起诉/答辩时，生成 `pleading_framework.md`。

必须包含：

- 文书类型和目标读者。
- 请求或抗辩目标。
- 事实叙事框架。
- 法律依据和法律规则适用边界。
- 证据附件地图。
- 备选请求、兜底主张或让步空间。
- 提交前必须核验的事实和表达风险。

除非用户明确要求并提供足够材料，不要直接把框架伪装成可提交的正式文书。

## 8. hearing_playbook.md

当事项进入调解、仲裁庭、诉讼庭审、行政听证或需要模拟追问时，生成 `hearing_playbook.md`。

必须包含：

- 听证/庭审目标。
- 主线案由或案件理论。
- 举证顺序。
- 质证或反驳重点。
- 对对方的合法发问。
- 裁判者可能追问。
- 风险问题和安全回答原则。
- 开庭前材料清单。

## 9. review_delta.md

后续出现新事实、新证据、新程序节点、新报价、对方材料或新合同版本时，不能重新开始。必须生成或更新 `review_delta.md`：

```markdown
# Review Delta

## 1. New Information

## 2. Affected Facts

## 3. Affected Issues

## 4. Changed Judgments
| Old Judgment | New Judgment | Why Changed | Confidence |
|---|---|---|---|

## 5. Impact On Claims / Defense / Strategy

## 6. Files To Update

## 7. Skills To Rerun
```

`review_delta.md` 必须说明哪些旧判断被加强、削弱、推翻或保持不变，并列明需要重跑的 skill 或工作文件。

## 10. Skill 编排

快速咨询层：

```text
privacy_scope_guard
→ case_intake_issue_map
→ case_dashboard.md
→ consultation_note.md
```

深度案件包层：

```text
timeline_evidence_ledger
→ elements_burden_matrix
→ case_reference_research
→ opponent_perspective
→ judge_perspective
→ strategy_risk_action
→ document_drafting 或 hearing_prep
→ case_package.md
→ final_synthesis
```

动态复盘层：

```text
review_learning_loop
→ review_delta.md
→ 只重跑受影响 skill
→ 更新 case_dashboard.md、case_package.md 和报告
```

## 11. 工作台检查

| 检查项 | 通过条件 | 未通过处理 |
|---|---|---|
| 案件驾驶舱 | 已有一句话案件地图、关键判断变量、争议焦点关系图、证明责任和可信度说明 | 不进入深度案件包；先补充 `case_dashboard.md` |
| 咨询纪要 | 用户能理解当前判断、限制、补证事项和不宜采取的动作 | 不把咨询纪要当作可交付意见 |
| 案件包 | 事实、证据、争议焦点、来源、对方视角、裁判视角和策略已串联 | 报告只能标记为阶段性或草稿 |
| 文书框架 | 文书目标、请求、事实、法律、证据附件和表达风险已明确 | 不输出可提交式文书 |
| 庭审/听证 | 庭审目标、举证顺序、质证、发问和裁判者追问已准备 | 不声称已完成庭审准备 |
| 复盘差异 | 新旧信息差异、受影响争议焦点、变化判断和需重跑文件已列明 | 不更新报告或必须标记复核不足 |

## 12. i18n 规则

- 中文事项使用 `案件驾驶舱`、`咨询纪要`、`案件包`、`文书框架`、`庭审手册` 等中文标题。
- 英文事项使用 `Case Dashboard`、`Consultation Note`、`Case Package`、`Pleading Framework`、`Hearing Playbook` 等英文标题。
- 内部文件名保持英文稳定，便于跨工具读取。
- 专有名词、合同原文、证据备注和当事人原话可保留原文，并用用户主语言解释。
